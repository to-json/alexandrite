# R2: Values stored into a caller's objects

R1 put a function's temporaries in its own region and its result in the caller's. What a function *stores into its caller's objects* still went to the program region, never freed. That covers a helper adding to a map it was given, or a `!` method growing one of its receiver's fields. A caller that builds a container per loop iteration and lets a helper fill it leaked everything the helper stored.

```ruby
def tally(m: Map[Str, Int], n: Int) {
  (1..20).each { m["word #{it % 7} of #{n}"] += 1 }
}
while i < 20000 {
  counts: Map[Str, Int] = {}
  tally(counts, i)          # the keys tally makes now live where `counts` does
  ...
}
```

| `mem/fill.alx` (release) | peak memory |
|---|---|
| R1 | 20 MB, growing with the iteration count |
| **R2** | **1 MB**, flat |

## How it works

- **A new place.** The escape analysis gives a value whose only long-lived destination is one parameter's storage (and nothing longer-lived) the place "into parameter p".
- **Where such a value is allocated**, in order of preference:
  1. At a store into a container (`<<`, `m[k] =`, `a[i] =`, field stores through `self`, `copy`), the region of the container's storage, looked up once for the store, its values and any growth.
  2. Otherwise, the region of the parameter's own storage. This case is the key built in a temporary before `m[k] += 1` stores it.
  3. If the parameter has no storage of its own (a struct passed by value), the program region, as before.
- **The runtime query `region_of(pointer)`** (built by a Sonnet agent) answers in one hash probe: which of this thread's regions holds this address, interior pointers included.
  - Chunks are now 1 MB-aligned, and every 1 MB granule of a chunk or large block is registered when it's acquired and removed when it's freed.
  - Anything else (literals, stack, runtime buffers, other threads' memory, NULL) answers "the program region", which is always safe.

## Also in this round (R4, started)

- **Lambdas capture variables, not copies (R5, replacing D16).**
  - A captured variable that changes after capture lives in a one-element slice cell. Slices share storage, so the lambda and the function see one variable: a counter works, closures keep state, and late binding sees the latest value.
  - `spawn` bodies and generators still copy (task boundary).
  - Test: `closures.alx`.
- **`!` methods through interfaces (R7).**
  - An interface can declare `def write!(s: Str) -> Int`. Calling it on an interface value in a variable, field or element mutates the value in place, which is Go's pointer receivers as used by `io.Writer`.
  - Dispatch hands each implementor's `!` method a cell of its own type, placed in the interface value's region, and writes it back.
  - Test: `writers.alx`.

## Not yet

- **R3:** long-lived containers that churn still keep replaced values until the container's region dies. This affects a cache map in `main` or one that lives as long as a server.
- **Interface methods:** `IfaceCall` is still treated as "escapes" by the analysis, so values passed to interface methods go to the program region.
