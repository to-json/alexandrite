# R3: Containers that churn

After R1 and R2, a map or pool that lives across a loop kept every value it had ever held until the function returned. Replacing `cache[key]` or removing a pool entry dropped the reference, but the bytes stayed in the region. A cache in `main`, or one that lives as long as a server loop, grew without bound.

Decision R11 (per-container regions with compaction, chosen over refcounting) fixes this for the common shape:

```ruby
cache: Map[Str, Str] = {}
while i < 300000 {
  key = "user#{i % 100}"
  cache[key] = "report #{i} for #{key}"   # replaces one of 100 entries
  i += 1
}
```

| release build, peak memory | before R3 | **R3** |
|---|---|---|
| `mem/churn.alx` (map, 300k replacements, 100 live) | 24 MB | **3 MB** |
| `mem/pchurn.alx` (pool, 200k adds and removes, 50 live) | 20 MB | **3 MB** |

## How it works

- **Owners.** The region analysis (`compiler/src/regions.rs`, `owners`) picks the map or pool locals that:
  - are made once, in the frame, and never reassigned;
  - are mutated inside a loop, where the def isn't in that loop;
  - don't escape: nothing connected to them reaches a return, a global or a caller.

  Every other local tied to the container must also be either fresh each iteration or used only after the loop. A local used only after the loop counts only if the loop isn't nested in another loop.
- **A child region per owner.** At its definition, the container's contents get a region of their own (`RegionNew`, a child of the frame). Everything stored into it is allocated there: keys, values, slot growth. The header records the region and its size after the last compaction.
- **Compaction at the top of each iteration** (while/loop bodies, and after each `each` element):
  - It runs when `region bytes > 3 × live bytes + 64 KB`.
  - The live contents are deep-copied into a fresh child region: a map is rebuilt from its entries, a pool's slot array is copied as-is.
  - The old region is freed in one call.

  The factor 3 keeps compaction from firing again on the very next iteration. The copied slot array has no spare capacity, so the next push doubles it.
- **Cost:** deterministic and amortized. Each compaction copies the live set, and the next one waits until garbage is at least twice that size. No global GC, and no change to the layout of slices or strings.

## Pools reuse slots

A pool's slot array used to grow by one per `add` forever, so churn through a pool was unbounded no matter how its region was handled.

- **Reuse.** Removed slots now go on a free list in the pool header, and `add` reuses them.
- **Generational handles.** A handle is `slot index | generation << 32`. A slot is live while its generation is odd. `remove` bumps it to even and `add` bumps it back to odd.
- **Stale handles still panic.** A handle to a removed slot still fails with "use of a removed pool handle", even after the slot is reused. `remove` with a stale handle returns none.
- **Printing** a handle shows only its index (`@3`), as before.

## Bugs found on the way

- **Push onto a non-empty subslice wrote past its end** (C runtime and JIT). D6 says a subslice has no spare capacity (cap 0), but push only grew when `len == cap`. Push now grows when `len >= cap`. `collections.alx` gains a case.
- **The Rust oracle had the same case wrong:** its new capacity underflowed when the slice was longer than 4.
- **`pool.remove(h)` as a statement** failed to compile in C because the result tuple type was never declared. The result is now bound to a typed temp.
- **Handles count as storage-free** in the escape analysis, so a list of handles no longer ties itself to the pool.

## Follow-up: views and named locals (port-issues #177)

An owner map stopped being one as soon as ordinary code touched it, which is what the language server does with its document map:

- **A helper indexing it by a key argument** (`def get(m, k) { m[k] }`). The lookup's value was aliased to the key as well as the map, so the map reached the caller's key and went to the program region. A map read now aliases the receiver only.
- **A named local holding what was read**, unless assigned by a top-level statement before any mention. Freshness is now definite assignment over one iteration: assigned on every path before each read (both `if` branches, or one when the other ends in `next`/`break`/`return`/`fail`). Assignments inside expressions, blocks and inner loops still don't count.

| release build, ALX_MEMSTATS peak (100 KB values, 3,000 replacements) | before | after |
|---|---|---|
| map passed to helpers that index it by key | 904 MB | **7.3 MB** |
| named locals in branches, `if old = m[k]`, slices of values | 901 MB | **7.3 MB** |
| `for k in m.keys`, `for k, v in m` with lookups | 7.3 MB | 7.3 MB |

Tests: `region_views.alx` (each shape, plus the unsafe ones: a local read in a later iteration than the one that set it, values, keys and helper results kept across iterations; with the checks disabled each crashes under ASan), and `mem/views.alx` in the bounded-memory checks.

## Follow-up: calls through interfaces (port-issues #178)

The language server's exec client grew about 85 KB per check. The call itself was not the cause: `client.check!(req)` through `[C: Client]` is monomorphised and used the instance's summary. Four over-approximations were:

- **An interface call's result** aliased the receiver and every argument. It now refers only to what some implementor returns (the join of their summaries). os/exec's `pump!` passes its 64 KB read buffer to `rd.read!(buf)` on an `io.Reader`; the error it returns no longer pins the buffer.
- **An interpolation** aliased its arguments. It is a new string, except `"#{a}#{b}"`, which C's two-part concatenation may answer with `a` or `b`.
- **`Str.from_bytes`** aliased its bytes. Every backend copies them.
- **A struct or list holding a string** was aliased back into the string, so one path shared by the exec command (program region) and a result entry pinned the result map. A string's bytes hold nothing, so neither `alias` nor the owner walk steps back from a holder into a string. A string stored into an owner goes into its region only if everything that holds it was checked.

| alx-lsp, exec client, 100 KB document, a check per edit | before | after |
|---|---|---|
| growth per check (300 vs 900 checks) | 85 KB | **17 KB** |
| `mem/iface.alx` (generic and interface client, 6,000 calls with 20 KB results) | 403 MB | **5 MB** |

Still open: about 10 KB per check stays in os/exec. The analysis is field-insensitive, so a `Cmd` whose channel, stdin text or context goes to a task takes its args and environment into the program region with it.

## Not yet

- **A container passed to other functions.** A container that is a parameter, or that is stored into a struct field, isn't an owner. That covers a cache handed to a request handler, which is the server shape. That needs owners to cross calls, together with R6's sharing rules.
- **Slice elements and struct fields that churn** (`xs[i] = new_string` in a long loop) still keep old values until the enclosing region dies.
- **The 64 KB floor** means small containers are never compacted. That's intentional.
