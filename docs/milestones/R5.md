# R5: M:N tasks

`spawn` used to start an OS thread with an 8 MB stack. Tasks are now coroutines multiplexed over one worker thread per core. The compiler didn't change: `alx_spawn`, `alx_task_wait`, channels and `select` keep their C ABI, and the JIT reaches them through the same shims. Built by a Sonnet agent from a spec.

| `mem/tasks.alx` (release): 100,000 tasks in a daisy chain | |
|---|---|
| Time | 0.67 s (JIT 1.0 s) |
| Peak region memory | 1 MB |
| RSS | 105 MB, about 1 KB per parked task |
| Before R5 | 100,000 OS threads: not feasible |

## Design

- **Context switch:** hand-written assembly for aarch64 and x86_64, saving the callee-saved registers and stack pointer. No `ucontext`.
- **Workers:** one per core (`ALX_PROCS` overrides), persistent, started at the first `spawn`. Each worker's run stack is 8 MiB of address space, committed only as it is touched (`ALX_TASK_STACK` overrides: bytes, or `512k`, `64m`, `1g`; at least 4 pages; JIT and compiled programs alike). New tasks go on a global queue that any free worker takes from. A woken task goes on its worker's local queue.
- **Stacks:** each worker has one 256 KiB run stack (`ALX_TASK_STACK` overrides) with a guard page. A task that parks copies its live part (typically about 1 KB) to the heap, and copies it back to the same addresses when it resumes. That's why 100,000 parked tasks cost about 100 MB.
- **Sanitizer builds** give each task a private stack instead, because ASan's and TSan's shadow memory is per address. They annotate every switch for the sanitizer.
- **Stack overflow:** a fault on the current task's guard page prints "alexandrite: stack overflow in a task".
- **Waiting:**
  - Each channel, each task (for `wait`) and each `Mutex` keeps a wait list, and a state change wakes only that list.
  - A waiter re-checks its condition after waking, so the channel logic didn't change.
  - Inside a task, waiting parks the coroutine. Main, which runs on its own OS stack, still blocks on a condvar.
- **Deadlock detection:** a count of running, queued and unstarted tasks (main included). When it reaches zero, main reports "all tasks are asleep: deadlock". That now also covers deadlocks among tasks only, while main waits on one of them.
- **Region state follows the task:** on a switch, the bump cache is flushed into the current region and the current region and task are saved, then restored on resume.

## Tasks stay on one worker

A task runs only on the worker that first ran it.

- **Why:** at `-O2`, clang keeps the address of the thread-local bump pointer in a callee-saved register across calls, `alx_chan_recv` included (seen in the arm64 assembly). A task resumed on another thread would keep allocating through the old thread's bump cache.
- **Cost:**
  - A woken task waits for its own worker.
  - A CPU-bound task that never blocks can starve the tasks queued behind it.
  - There's no work stealing.
- **The fix,** later: reach the allocator state through the current worker's structure (a register or a call clang can't cache) instead of C thread-locals. Migration and a global `region_of` registry would come with it.

## Why this wasn't stdlib work

The scheduler is runtime: context switches, queues and parking. The I/O event loop is the part that needs the standard library. With it, a socket read parks the task instead of blocking its worker. It comes with `net` in L3. Until then, a blocking system call blocks its worker.

- `mem/tasks.alx` (R5 checks): the release build's output and its region and RSS bounds, plus the JIT.
- `compiler/runtime/tests/tasks_test.c` passes plain, under ASan and under TSan, with 1 and 3 workers. It covers:
  - the 100,000-task chain;
  - tasks that park while inside regions;
  - stack overflow;
  - deadlock.
- `concurrency.alx` and `concurrency.deadlock.alx` are unchanged on every backend.
- `sync.alx` (R6's `Mutex`) runs on the new wait lists.
- Acceptance: **193 of 193 checks pass.**

## Not yet

- Task migration, work stealing, and a global `region_of` registry (see above).
- **One global lock** guards every channel and queue. The chain is faster with 1 worker (about 40 ms) than with 11 (about 450 ms), because every hop is a cross-worker wake through that lock. Scheduling and locking are the next target.
- **The I/O event loop** comes with `net` (L3).
